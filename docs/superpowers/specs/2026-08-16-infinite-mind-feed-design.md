# MIND 无限信息流与实体标签设计

## 目标

把当前一次只展示 10 篇新闻的首页升级为新闻 App 式连续信息流，并在文章详情页展示由 MIND `title_entities`、`abstract_entities` 解析得到的实体标签。

## 已确认的产品行为

- 首页首次加载 20 篇，接近列表底部时自动追加 20 篇。
- 同一信息流会话内按 `news_id` 严格去重；刷新推荐或切换画像开始新会话。
- 已有新闻在追加失败时继续保留，并提供明确的重试入口。
- 后端返回 `next_cursor` 与 `has_more`；前端不推测是否还有数据。
- 复用 `feed_request` 保存会话分页状态和已返回新闻，不新增新闻主表或信息流业务表。
- `mind_news` 继续保持 MIND `news.tsv` 的八个原始字段，不加入展示或推荐字段。
- 实体只在详情页展示，合并标题实体和摘要实体后去重，并分为人物、机构、地点、其他实体。
- Wikidata ID、置信度、表面形式和来源字段通过接口保留，但页面默认只显示可读标签和类型。

## 无限滚动数据流

1. 前端以无游标请求首批 20 篇，后端创建一个信息流会话。
2. 后端在现有 `feed_request` 行记录会话 ID、页码、返回的新闻 ID 和下一游标。
3. 下一次请求携带游标，后端校验游标归属、用户、页面大小和实验参数。
4. 候选生成继续使用个性化主题、ALS、搜索意图、热门内容、赞助内容与全目录探索。
5. 后端排除会话中已返回的新闻；候选不足时从完整 `mind_news` 目录补充未展示新闻。
6. 响应返回本页请求 ID、20 篇以内新闻、下一游标以及是否仍有未展示新闻。
7. 前端按页保存请求 ID，确保曝光、点击和赞助归因使用新闻所属页面的请求 ID。

## 接口变化

`GET /feed` 新增可选查询参数 `cursor`。`FeedResponse` 新增：

- `next_cursor: string | null`
- `has_more: boolean`

`GET /articles/{news_id}` 新增：

- `title_entities: ArticleEntity[]`
- `abstract_entities: ArticleEntity[]`

`ArticleEntity` 包含 `label`、`entity_type`、`type_code`、`wikidata_id`、`confidence`、`surface_forms`。类型码 `P`、`O`、`G` 分别映射为人物、机构、地点，其余有效类型映射为其他实体。

## 前端状态

前端以页为单位保存 `{requestId, items}`，再生成去重后的可见列表。IntersectionObserver 观察列表尾部哨兵；加载中、失败、可重试和全部加载完毕都有独立状态。每条新闻保留所属页的 `requestId`，不能用最新一页请求 ID 覆盖旧新闻的归因。

详情页在摘要下方增加“相关实体”区域。标签按类型分组，同一 Wikidata ID 优先去重；缺少 Wikidata ID 时按规范化标签去重。空实体数组时不渲染该区域。

## 错误与边界

- 无效、过期或不属于当前用户的游标返回 400/409，不静默开启新会话。
- 重复提交同一个页请求 ID 保持现有幂等参数校验。
- 客户端对 `news_id` 再做一层防御性去重。
- 连续追加失败不清空已有列表；用户可手动重试。
- 画像切换、刷新推荐或路由会话变化时取消旧请求并清空旧游标。
- 实体 JSON 中缺少标签、类型错误或字段不完整的元素被忽略，不影响详情页主体。

## 验收标准

- 首屏请求 20 篇，触底后追加下一批，页面已加载数量持续增加。
- 同一会话多批次无重复 `news_id`，每条曝光和点击使用正确的页请求 ID。
- 后端可持续从 65,238 篇目录中补充未展示新闻。
- 详情页能显示人物、机构、地点和其他实体标签。
- MIND 八字段数据库契约保持不变。
- Python、PostgreSQL、前端测试、前端构建和真实页面验证通过。
